Definition — learn this wording

The relational model represents all data as relations — two-dimensional tables of rows and columns — and represents the connections between them using keys rather than pointers or links.

That is the whole idea, and its power is that it needs only one shape. A student, a course, and the enrolment joining them are all the same kind of object: a table. Nothing else has to be learned.

It was proposed by E. F. Codd in 1970 and is the model behind MySQL, Oracle, PostgreSQL and MS Access.

परिभाषा — यही शब्दमा सम्झनुहोस्

रिलेसनल मोडेल ले सबै data लाई रिलेसन — पङ्क्ति र स्तम्भ भएका दुई आयामिक तालिका — का रूपमा राख्छ, र तिनबीचको जोडाइ pointer वा link होइन, कुञ्जी ले देखाउँछ।

पूरा विचार यत्ति हो, र यसको बल एउटै आकार चाहिनुमा छ। विद्यार्थी, विषय, र दुवैलाई जोड्ने भर्ना — तीनै उही किसिमका वस्तु हुन्: तालिका। अरू केही सिक्नु पर्दैन।

यो E. F. Codd ले सन् १९७० मा प्रस्ताव गरेका हुन्, र MySQL, Oracle, PostgreSQL तथा MS Access यसैमा आधारित छन्।

3.2  The vocabulary, on one table

Nine words, six things

This topic is a list of terms, and lists of terms are what students confuse in the hall. The pair that goes wrong most is degree and cardinality: they sound interchangeable and they are not.

Degree is the number of columns. Cardinality is the number of rows. A table with 4 columns and 100 rows has degree 4 and cardinality 100 — the numbers are usually nothing alike, so if you can remember which is which you can always check your own answer.

Rather than memorising nine definitions, point at them. Use the tool below: choose a word and the part of the table it names lights up.

नौ शब्द, छ वस्तु

यो टपिक शब्दहरूको सूची हो, र परीक्षा हलमा विद्यार्थीले अलमल्ने ठाउँ यस्तै सूची हुन्। सबैभन्दा बढी बिग्रने जोडी degree र cardinality हो: सुन्दा उस्तै लाग्छ, तर होइन।

3.3 — The properties of a relation. Every cell holds a single, atomic value — never a list. No two rows are identical — the primary key guarantees it. The order of rows does not matter, and neither does the order of columns — a table is a set, not a list. Every value in a column comes from the same domain. रिलेसनका गुण: हरेक कक्षमा एउटै अविभाज्य मान हुन्छ — सूची कहिल्यै होइन। दुई पङ्क्ति उस्तै हुँदैनन् — primary key ले सुनिश्चित गर्छ। पङ्क्तिको क्रमले फरक पार्दैन, स्तम्भको क्रमले पनि — तालिका सेट हो, सूची होइन। एउटै स्तम्भका सबै मान उही domain बाट आउँछन्।

Predict first · पहिले अनुमान गर्नुहोस्

Two tables hold exactly the same four rows, but one lists them in a different order. Are they the same relation? दुई तालिकामा ठ्याक्कै उही चार पङ्क्ति छन्, तर एउटामा क्रम फरक छ। के ती एउटै रिलेसन हुन्?

Yes. A relation is a set of tuples, and a set has no order. This is why you must write ORDER BY when you want a particular order — the database is under no obligation to give you the rows in the order they were inserted, and without ORDER BY it may give a different order each time.

हो। रिलेसन भनेको ट्युपलहरूको सेट हो, र सेटको क्रम हुँदैन। त्यसैले निश्चित क्रम चाहिँदा ORDER BY लेख्नैपर्छ — डाटाबेसले भर्ना गरेकै क्रममा दिनुपर्ने बाध्यता छैन।

3.4  Mapping the ER model to the relational model

Four rules, applied in order

1. Every entity becomes a table. Its key attribute becomes the primary key, and every other attribute becomes a column.

2. A 1:M relationship is recorded by putting the primary key of the "one" side into the "many" side as a foreign key. No extra table.

3. A M:N relationship becomes a table of its own, holding the primary key of each side as a foreign key. Together those two columns form its composite primary key.

4. A multivalued attribute becomes a separate table too — a column can hold only one value, so two phone numbers cannot live in one cell.

चार नियम, यही क्रममा

१. हरेक इन्टिटी तालिका बन्छ। यसको कुञ्जी एट्रिब्युट primary key बन्छ, र बाँकी हरेक एट्रिब्युट एउटा स्तम्भ।

२. 1:M सम्बन्ध लाई "एक" तर्फको primary key लाई "धेरै" तर्फ foreign key बनाएर राखिन्छ। थप तालिका चाहिँदैन।

३. M:N सम्बन्ध आफैं एउटा तालिका बन्छ, जसमा दुवैतर्फको primary key foreign key भएर बस्छ। ती दुई स्तम्भ मिलेर composite primary key बन्छ।

४. बहुमान एट्रिब्युट पनि छुट्टै तालिका बन्छ — स्तम्भले एउटै मान राख्ने भएकाले दुई फोन नम्बर एउटै कक्षमा बस्न सक्दैनन्।

Example 1 Converting an ER diagram to tables

Question: a hospital records DOCTORs (doctor_id, name) and PATIENTs (patient_id, name). A doctor treats many patients, and a patient may be treated by many doctors. Convert this to the relational model.

Step 1 — apply rule 1 to each entity:

Working
Doctor ( doctor_id, name ) PK Patient ( patient_id, name ) PK

Step 2 — decide the cardinality. Many doctors to many patients, in both directions, so it is M:N. Rule 3 applies: the relationship gets a table of its own.

Answer
Doctor ( doctor_id, name ) Patient ( patient_id, name ) Treats ( doctor_id, patient_id ) FK FK composite primary key = both columns together

Three tables from two entities. Marks are lost here by producing only two and trying to squeeze the relationship into a single column — which cannot work, because a column holds one value and this doctor has many patients. दुई इन्टिटीबाट तीन तालिका। यहाँ अंक जाने ठाउँ: दुई मात्र बनाएर सम्बन्धलाई एउटै स्तम्भमा कोच्न खोज्नु — जुन सम्भव छैन, किनभने स्तम्भले एउटै मान राख्छ र यो डाक्टरका धेरै बिरामी छन्।

Keys, and the rule that links two tables

What you will learn: how a foreign key in one table points at a primary key in another, and what referential integrity actually forbids. तपाईंले के सिक्नुहुन्छ: एउटा तालिकाको foreign key ले अर्कोको primary key लाई कसरी देखाउँछ, र referential integrity ले साँच्चै के निषेध गर्छ।

What to notice

Read the two badges. PK marks the column that identifies a row; FK marks the column that points at another table.

Student.class_id holds 10, 10 and 11 — values that all exist in Class.class_id. That is referential integrity: a foreign key may not hold a value that has no matching primary key. Inserting a student in class 15 would be refused, because no class 15 exists.

Gita's class_id is NULL, and that is allowed. A foreign key may be empty — it means "not assigned yet". It may not be wrong.

दुई ब्याज पढ्नुहोस्। PK ले पङ्क्ति चिनाउने स्तम्भ, FK ले अर्को तालिका देखाउने स्तम्भ जनाउँछ। Student.class_id मा १०, १०, ११ छन् — सबै Class.class_id मा भएका मान। यही referential integrity हो। कक्षा १५ मा विद्यार्थी थप्न खोजे अस्वीकार हुन्छ। गीताको class_id NULL छ, र त्यो मिल्छ — foreign key खाली हुन पाउँछ, गलत हुन पाउँदैन।
Example 2 Labelling a table with the right term for every part

Question: for the table below, state the relation name, the degree, the cardinality, the primary key, and the domain of marks.

Given
Student ┌────┬───────┬───────┬──────────┐ │ id │ name │ marks │ class_id │ ├────┼───────┼───────┼──────────┤ │ 1 │ Ram │ 78 │ 10 │ │ 2 │ Sita │ 91 │ 10 │ │ 3 │ Hari │ 55 │ 11 │ └────┴───────┴───────┴──────────┘

Count sideways for degree, downwards for cardinality. That one sentence prevents the only mistake this question invites:

Answer
Relation name Student Degree 4 (id, name, marks, class_id — count COLUMNS) Cardinality 3 (three tuples — count ROWS) Primary key id (unique, and never NULL) Domain of marks whole numbers 0–100 Attribute one column, e.g. name Tuple one row, e.g. (2, Sita, 91, 10)

Write the two counts with the words "columns" and "rows" beside them, as above. A marker reading "Degree 4, Cardinality 3" cannot tell whether you knew which was which or guessed; "Degree 4 columns, Cardinality 3 rows" removes the doubt. दुई गणनासँगै "स्तम्भ" र "पङ्क्ति" शब्द लेख्नुहोस्। "Degree ४, Cardinality ३" मात्र लेखे परीक्षकले जानेर लेखेको कि अनुमान गरेको भन्न सक्दैनन्; शब्द थपे शङ्का हट्छ।

Mistakes that cost marks here

  • Swapping degree and cardinality. Degree counts columns; cardinality counts rows. Check your answer against the table — the two numbers are almost never the same. Degree र cardinality साट्नु। Degree ले स्तम्भ, cardinality ले पङ्क्ति गन्छ। तालिकासँग मिलाएर जाँच्नुहोस्।
  • Saying a relation may have duplicate rows. It may not — that is one of the defining properties. रिलेसनमा उही पङ्क्ति दोहोरिन सक्छ भन्नु। सक्दैन — यो परिभाषित गुण मध्येको एक हो।
  • Turning an M:N relationship into two tables. It needs three. The relationship itself becomes a table. M:N सम्बन्धलाई दुई तालिका बनाउनु। तीन चाहिन्छ — सम्बन्ध आफैं तालिका बन्छ।
  • Confusing schema with instance. Inserting a row changes the instance. The schema is unchanged. Schema र instance मिसाउनु। पङ्क्ति थप्दा instance बदलिन्छ, schema होइन।
  • Putting a list in a cell. "Maths, Science" in one cell breaks the atomic-value property — and it is exactly what 1NF exists to fix, in Unit 5. एउटै कक्षमा सूची राख्नु। "Maths, Science" ले अविभाज्य मानको गुण तोड्छ — र युनिट ५ को 1NF यही सुधार्न छ।

Exam focus — what is asked from this unit

Two question shapes dominate here. The first gives you a small table and asks you to state its degree, its cardinality and its primary key — a few marks, quickly earned, provided you do not swap the first two. The second gives you an ER diagram and asks you to convert it to tables; the marks are for the right number of tables and for putting the foreign key on the correct side. यहाँ दुई किसिमका प्रश्न हावी छन्। पहिलोले सानो तालिका दिएर degree, cardinality र primary key सोध्छ — छिटो पाइने अंक, पहिला दुई नसाटे। दोस्रोले ER चित्र दिएर तालिकामा बदल्न भन्छ; अंक सही सङ्ख्या का तालिका र foreign key सही तर्फ राखेकोमा हुन्छ।
2 marks Practice question

Define degree and cardinality of a relation. रिलेसनको degree र cardinality परिभाषित गर्नुहोस्।

The degree of a relation is the number of attributes (columns) in it.

The cardinality of a relation is the number of tuples (rows) in it.

Example: a Student table with columns id, name, marks, class_id and 4 rows has degree 4 and cardinality 4.

दुवैको परिभाषा र एउटा उदाहरण। स्तम्भ = degree, पङ्क्ति = cardinality।
3 marks Practice question

State any three properties of a relation. रिलेसनका कुनै तीन गुण लेख्नुहोस्।

Atomic values — every cell holds a single indivisible value, never a list. No duplicate tuples — no two rows are identical, which the primary key guarantees. Order is not significant — the rows and the columns may be listed in any order. Values come from a domain — every value in a column is drawn from the same allowed set. Each attribute has a distinct name.

Any three, each named and explained in one line.

कुनै तीन — नाम दिएर एक–एक हरफमा व्याख्या गर्नुहोस्।
4 marks Practice question

A school has CLASS (class_id, room) and STUDENT (student_id, name). A class contains many students, and each student belongs to one class. Convert this ER model to the relational model and mark the keys. एउटा विद्यालयमा CLASS (class_id, room) र STUDENT (student_id, name) छन्। एउटा कक्षामा धेरै विद्यार्थी हुन्छन्, र हरेक विद्यार्थी एउटै कक्षाको हुन्छ। यसलाई रिलेसनल मोडेलमा बदलेर कुञ्जी देखाउनुहोस्।

Class ( class_id, room ) PK Student ( student_id, name, class_id ) PK FK → Class.class_id

The relationship is 1:M, so rule 2 applies: no third table. The primary key of the "one" side (Class) goes into the "many" side (Student) as a foreign key.

One mark per table, one for the primary keys, one for the foreign key on the correct side. Putting student_id into Class instead would be wrong — a class has many students, so that column could not hold them all.

सम्बन्ध 1:M भएकाले नियम २ लाग्छ: तेस्रो तालिका चाहिँदैन। "एक" तर्फ (Class) को primary key "धेरै" तर्फ (Student) मा foreign key भएर जान्छ। उल्टो गर्दा गलत हुन्छ।

Key points to revise — दोहोर्‍याउनुपर्ने मुख्य बुँदा

  • The relational model stores everything as tables and links them with keys, not pointers. Proposed by E. F. Codd, 1970. रिलेसनल मोडेलले सबै कुरा तालिकामा राख्छ र pointer होइन, कुञ्जीले जोड्छ। E. F. Codd, सन् १९७०।
  • Degree = number of columns. Cardinality = number of rows. Do not swap them. Degree = स्तम्भ सङ्ख्या। Cardinality = पङ्क्ति सङ्ख्या। नसाट्नुहोस्।
  • Schema is the structure; instance is the data in it right now. Schema संरचना हो; instance अहिलेको data।
  • A relation holds atomic values, no duplicate rows, and no significant order. रिलेसनमा अविभाज्य मान हुन्छन्, उही पङ्क्ति दोहोरिँदैन, र क्रमको महत्त्व हुँदैन।
  • ER → tables: every entity a table; 1:M puts a foreign key in the many side; M:N makes a third table; a multivalued attribute makes its own table. ER → तालिका: हरेक इन्टिटी एउटा तालिका; 1:M मा "धेरै" तर्फ foreign key; M:N ले तेस्रो तालिका; बहुमान एट्रिब्युटले आफ्नै तालिका।
  • Referential integrity: a foreign key may be NULL, but it may never hold a value that does not exist in the table it points at. Referential integrity: foreign key NULL हुन सक्छ, तर देखाइएको तालिकामा नभएको मान कहिल्यै राख्न पाउँदैन।
