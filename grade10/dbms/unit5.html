5

Relational Database Design

रिलेसनल डाटाबेस डिजाइन

8 hrs · 6 marks

By the end of this unit you can…

  1. Define functional dependency and read the notation A → B.
  2. Identify a full, a partial and a transitive dependency.
  3. Define normalization and say what problem it exists to solve.
  4. State the rule for 1NF, 2NF and 3NF.
  5. Normalise a small table to 3NF, naming the anomaly removed at each step.
यो युनिट सकिँदा: functional dependency परिभाषित गर्न र A → B पढ्न, full–partial–transitive निर्भरता चिन्न, normalization के हो र किन चाहिन्छ भन्न, 1NF–2NF–3NF का नियम भन्न, र सानो तालिकालाई हरेक चरणमा हट्ने समस्याको नाम दिँदै 3NF सम्म लैजान सक्नुहुनेछ।
Why a table can be "wrong" even when it works

A table can hold correct data today and still be badly designed. The test is what happens when it changes.

Put the class's room number on every student row, and you have written the same fact forty times. Change the room and you must find all forty. Miss one and the database now disagrees with itself. That is an update anomaly.

Delete the last student in a class, and the room number disappears with them, even though the room still exists — a deletion anomaly. And a new class with no students yet cannot be recorded at all — an insertion anomaly.

Normalization exists to remove these three anomalies. Saving disk space is a side effect, not the purpose.

काम गरिरहेको तालिका पनि किन "गलत" हुन सक्छ

तालिकामा आज सही data होला, तर डिजाइन नराम्रो हुन सक्छ। जाँच त्यो बदलिँदा के हुन्छ भन्नेमा हो।

कक्षाको कोठा नम्बर हरेक विद्यार्थीको पङ्क्तिमा राख्नुभयो भने उही तथ्य चालीस पटक लेखिन्छ। कोठा बदल्दा चालीसै ठाउँ खोज्नुपर्छ। एउटा छुट्यो भने डाटाबेस आफैंसँग बाझिन्छ। यही update anomaly हो।

कक्षाको अन्तिम विद्यार्थी हटाउँदा कोठा नम्बर पनि सँगै हराउँछ, कोठा भने रहन्छ — deletion anomaly। र विद्यार्थी नभएको नयाँ कक्षा राख्नै सकिँदैन — insertion anomaly।

Normalization यी तीन anomaly हटाउन छ। डिस्क बचत यसको उद्देश्य होइन, सहायक असर हो।

5.1  Functional dependency

Definition — learn this wording

Attribute B is functionally dependent on attribute A, written A → B, if each value of A determines exactly one value of B.

Read A → B as "A determines B". In a Student table, student_id → name: give me the id and the name is fixed. The reverse is not true — two students may share a name, so name → student_id does not hold.

Full dependency — B depends on the whole key. Partial dependency — B depends on only part of a composite key. Transitive dependency — A → B and B → C, so A → C through a non-key column.

Those three names are the whole of this topic, and each one is removed by one normal form.

परिभाषा — यही शब्दमा सम्झनुहोस्

एट्रिब्युट B, एट्रिब्युट A मा functionally dependent छ — A → B लेखिन्छ — यदि A को हरेक मानले B को ठ्याक्कै एउटा मान तय गर्छ भने।

A → B लाई "A ले B तय गर्छ" भनेर पढ्नुहोस्। Student तालिकामा student_id → name: id दिए नाम निश्चित हुन्छ। उल्टो भने होइन — दुई विद्यार्थीको नाम उही हुन सक्छ।

Full dependency — B पूरै कुञ्जीमा निर्भर। Partial dependency — B composite कुञ्जीको एक भाग मा मात्र निर्भर। Transitive dependency — A → B र B → C, त्यसैले कुञ्जी नभएको स्तम्भ हुँदै A → C।

यी तीन नाम नै यो टपिकको सार हुन्, र हरेकलाई एउटा normal form ले हटाउँछ।

Each normal form removes exactly one named problem. 1NF removes repeating groups — a cell holding more than one value. 2NF removes partial dependency. 3NF removes transitive dependency. Say the name of the problem in your answer; that is what the marks are for. हरेक normal form ले ठ्याक्कै एउटा नामअङ्कित समस्या हटाउँछ। 1NF ले दोहोरिने समूह — एउटै कक्षमा एकभन्दा बढी मान। 2NF ले partial dependency। 3NF ले transitive dependency। उत्तरमा समस्याको नाम लेख्नुहोस्; अंक त्यसैको हो।

Predict first · पहिले अनुमान गर्नुहोस्

A table has the composite key (student_id, subject) and also holds the student's name. What kind of dependency is student_id → name? एउटा तालिकाको composite कुञ्जी (student_id, subject) छ र विद्यार्थीको नाम पनि छ। student_id → name कस्तो निर्भरता हो?

Partial. The key is both columns together, but name depends on only student_id — half the key. That is the definition of a partial dependency, and it is exactly what 2NF removes. A partial dependency is only possible when the key is composite; with a single-column key there is no "part" of it to depend on.

Partial। कुञ्जी दुवै स्तम्भ मिलेर हो, तर name student_id मा मात्र निर्भर छ — आधा कुञ्जीमा। partial dependency को परिभाषा यही हो, र 2NF ले हटाउने पनि यही। कुञ्जी composite भएमा मात्र partial dependency सम्भव हुन्छ।

5.2 & 5.3  Normalization to 3NF

step 0 / 4
The three rules, stated exactly

First Normal Form (1NF). A relation is in 1NF if every attribute holds only atomic (single) values and there are no repeating groups.

Second Normal Form (2NF). A relation is in 2NF if it is in 1NF and every non-key attribute is fully functionally dependent on the whole primary key — that is, no partial dependency.

Third Normal Form (3NF). A relation is in 3NF if it is in 2NF and no non-key attribute depends on another non-key attribute — that is, no transitive dependency.

Notice the shape: each form includes the one before it. A table cannot be in 3NF without already being in 2NF and 1NF, which is why they are always applied in order.

तीन नियम, ठ्याक्कै

First Normal Form (1NF). हरेक एट्रिब्युटले अविभाज्य (एउटै) मान मात्र राखेको र दोहोरिने समूह नभएको रिलेसन 1NF मा हुन्छ।

Second Normal Form (2NF). 1NF मा भएको र हरेक कुञ्जी–बाहेकको एट्रिब्युट पूरै primary key मा पूर्ण रूपमा निर्भर भएको — अर्थात् partial dependency नभएको।

Third Normal Form (3NF). 2NF मा भएको र कुनै पनि कुञ्जी–बाहेकको एट्रिब्युट अर्को कुञ्जी–बाहेकको एट्रिब्युटमा निर्भर नभएको — अर्थात् transitive dependency नभएको।

बनावट हेर्नुहोस्: हरेक रूपले अघिल्लोलाई समेट्छ। 1NF र 2NF नभई 3NF हुन सक्दैन, त्यसैले क्रमैसँग लागू गरिन्छ।

Example 1 Normalising a table to 3NF, step by step

Question: normalise this table to 3NF, naming the problem removed at each step.

Given
Student( roll, name, class_id, class_room, subjects ) roll name class_id class_room subjects 1 Ram 10 A-1 Maths, Science 2 Sita 10 A-1 Maths 3 Hari 11 B-2 Science

Step 1 — 1NF. The subjects cell holds two values. Split it so every cell holds one value; the key becomes (roll, subject):

1NF
Student( roll, subject, name, class_id, class_room ) 1 Maths Ram 10 A-1 1 Science Ram 10 A-1 2 Maths Sita 10 A-1 3 Science Hari 11 B-2 Problem removed: repeating group

Step 2 — 2NF. The key is (roll, subject), but name, class_id and class_room depend on roll alone — a partial dependency. Split the table:

2NF
Student( roll, name, class_id, class_room ) Takes ( roll, subject ) Problem removed: partial dependency

Step 3 — 3NF. In Student, class_room depends on class_id, which depends on roll — a transitive dependency through a non-key column. Move it out:

3NF — answer
Student( roll, name, class_id ) FK → Class.class_id Class ( class_id, class_room ) Takes ( roll, subject ) Problem removed: transitive dependency

Three tables, and now each fact is written once. Change room A-1 and you change one row, not forty. That is the anomaly gone, which is the whole point — write that sentence in your answer and you have shown you understand normalization rather than memorised it. तीन तालिका, र अब हरेक तथ्य एक पटक मात्र लेखिएको छ। कोठा A-1 बदल्दा एउटै पङ्क्ति बदलिन्छ, चालीस होइन। anomaly हट्यो — उत्तरमा यही वाक्य लेख्नुभयो भने घोकेको होइन, बुझेको देखिन्छ।

Practise the judgement · निर्णय अभ्यास गर्नुहोस्

Which normal form does this table break?

What you will learn: to spot the FIRST rule a table breaks, which is the whole skill the exam question tests. Knowing the three definitions is not the same as being able to apply them to a table you have not seen. तपाईंले के सिक्नुहुन्छ: तालिकाले पहिले कुन नियम तोड्छ भनी चिन्न — परीक्षाले जाँच्ने सीप यही हो। तीन परिभाषा जान्नु र नदेखेको तालिकामा लागू गर्न सक्नु फरक कुरा हुन्।

How to use this

Work down the forms in order every time: is every cell atomic? then is there a partial dependency? then a transitive one? The first "no" is your answer, and a table that breaks 1NF is not yet worth testing against 2NF.

Read the reason even when you are right. On the last case nothing is wrong at all — recognising a table that is already in 3NF is as examinable as fixing one that is not.

सधैं क्रमैसँग हेर्नुहोस्: हरेक कक्ष अविभाज्य छ? अनि partial निर्भरता छ? अनि transitive? पहिलो "छैन" नै उत्तर हो। सही भए पनि कारण पढ्नुहोस् — अन्तिम केसमा केही गलत छैन, र पहिले नै 3NF मा भएको तालिका चिन्न सक्नु पनि उत्तिकै सोधिन्छ।
Example 2 Naming the dependency before you split

Question: in Enrol( student_id, course_id, student_name, course_fee ) with the key (student_id, course_id), name every dependency and say which normal form fails.

Step 1 — write the dependencies out. This is the step students skip, and it is where the marks are:

Working
student_id → student_name course_id → course_fee (student_id, course_id) → nothing else

Step 2 — test each against the key. Both student_name and course_fee depend on half the key, not the whole of it. Two partial dependencies.

Answer
Fails 2NF — partial dependency (two of them). Enrol ( student_id, course_id ) Student( student_id, student_name ) Course ( course_id, course_fee )

Notice the key is composite, which is what makes a partial dependency possible at all. If the key had been a single column, this table would already have been in 2NF and you would have gone straight to looking for a transitive dependency. कुञ्जी composite छ — त्यसैले partial निर्भरता सम्भव भयो। कुञ्जी एउटै स्तम्भको भएको भए यो तालिका पहिले नै 2NF मा हुन्थ्यो र सिधै transitive निर्भरता खोज्नुपर्थ्यो।

Practise it — the help comes away · अभ्यास गर्नुहोस् — सहयोग घट्दै जान्छ

Mistakes that cost marks here

  • Saying normalization is done to save space. It is done to remove insertion, deletion and update anomalies. Space is a side effect. Normalization ठाउँ बचाउन गरिन्छ भन्नु। यो insertion, deletion र update anomaly हटाउन गरिन्छ। ठाउँ बचत सहायक असर हो।
  • Jumping straight to 3NF. The marks are for the steps. Show 1NF, then 2NF, then 3NF, and name the problem removed at each one. सिधै 3NF मा पुग्नु। अंक चरणका लागि हुन्। 1NF, 2NF, 3NF देखाउनुहोस् र हरेकमा हटेको समस्याको नाम लेख्नुहोस्।
  • Looking for a partial dependency when the key is a single column. There is no "part" of a one-column key, so a table with a simple key that is in 1NF is automatically in 2NF. एउटै स्तम्भको कुञ्जीमा partial dependency खोज्नु। एक–स्तम्भे कुञ्जीको "भाग" हुँदैन, त्यसैले 1NF मा भएको त्यस्तो तालिका आफैं 2NF मा हुन्छ।
  • Forgetting the foreign key after splitting. When Class is split out, Student must keep class_id to point back at it — otherwise the link is lost. छुट्याएपछि foreign key बिर्सनु। Class छुट्टिएपछि Student मा class_id रहनुपर्छ, नत्र जोडाइ हराउँछ।

Normalise to remove anomalies, not to save space. Space is a side effect. Anomaly हटाउन normalise गरिन्छ, ठाउँ बचाउन होइन। ठाउँ त सँगै आउने कुरा हो।

Exam focus — what is asked from this unit

This unit is examined by doing, not by describing. The standard question hands you one badly designed table and asks you to normalise it to 3NF. It is worth several marks and they are given per step, so a partial answer that gets to 2NF correctly still earns most of them — but only if you show the intermediate tables and name the dependency you removed. Never present just the final three tables. यो युनिट वर्णन गरेर होइन, गरेर जाँचिन्छ। सामान्य प्रश्नले नराम्रो डिजाइनको एउटा तालिका दिएर 3NF सम्म लैजान भन्छ। अंक चरणअनुसार दिइन्छ, त्यसैले 2NF सम्म सही पुगेको अपूरो उत्तरले पनि धेरै अंक पाउँछ — तर बीचका तालिका देखाएर हटेको निर्भरताको नाम लेखेमा मात्र। अन्तिम तीन तालिका मात्र नलेख्नुहोस्।
2 marks Practice question

Define normalization. Why is it needed? Normalization को परिभाषा दिनुहोस्। यो किन चाहिन्छ?

Normalization is the process of organising the attributes and relations of a database to reduce data redundancy and remove undesirable characteristics such as insertion, deletion and update anomalies.

It is needed because a table that repeats the same fact in many rows can be left inconsistent when one copy is changed and the others are not.

परिभाषा र किन चाहिन्छ — तीनै anomaly को नाम लिनुहोस्।
3 marks Practice question

State the conditions for 1NF, 2NF and 3NF. 1NF, 2NF र 3NF का सर्त लेख्नुहोस्।

1NF every attribute holds atomic (single) values, and there are no repeating groups 2NF in 1NF, AND every non-key attribute is fully dependent on the whole primary key (no partial dependency) 3NF in 2NF, AND no non-key attribute depends on another non-key attribute (no transitive dependency)

One mark each. Note that 2NF and 3NF both begin by requiring the previous form.

एक–एक अंक। 2NF र 3NF दुवै अघिल्लो रूपको माग गर्दै सुरु हुन्छन्।
4 marks Practice question

Normalise the following to 3NF, showing each step: Order( order_id, item, customer_id, customer_city ), where an order may contain several items. निम्नलाई चरणसहित 3NF सम्म लैजानुहोस्: Order( order_id, item, customer_id, customer_city ), जहाँ एउटा अर्डरमा धेरै सामान हुन सक्छन्।

1NF one row per item, key = (order_id, item) Order( order_id, item, customer_id, customer_city ) removed: repeating group 2NF customer_id and customer_city depend on order_id alone — a PARTIAL dependency Order( order_id, customer_id, customer_city ) Items( order_id, item ) removed: partial dependency 3NF customer_city depends on customer_id, which depends on order_id — a TRANSITIVE dependency Order ( order_id, customer_id ) Customer( customer_id, customer_city ) Items ( order_id, item ) removed: transitive dependency

One mark for each normal form reached correctly, and one for naming the dependency removed at each step.

सही पुगेको हरेक normal form लाई एक अंक, र हरेक चरणमा हटेको निर्भरताको नाम लेखेकोमा एक।

Key points to revise — दोहोर्‍याउनुपर्ने मुख्य बुँदा

  • Normalization removes insertion, deletion and update anomalies. Saving space is a side effect, not the reason. Normalization ले insertion, deletion र update anomaly हटाउँछ। ठाउँ बचत कारण होइन, सहायक असर हो।
  • A → B means A determines B — one value of A gives exactly one value of B. A → B को अर्थ A ले B तय गर्छ — A को एउटा मानले B को ठ्याक्कै एउटा मान दिन्छ।
  • 1NF removes repeating groups. 2NF removes partial dependency. 3NF removes transitive dependency. One form, one named problem. 1NF ले दोहोरिने समूह, 2NF ले partial dependency, 3NF ले transitive dependency हटाउँछ। एउटा रूप, एउटा नामअङ्कित समस्या।
  • A partial dependency needs a composite key. With a single-column key, 1NF already gives you 2NF. Partial dependency लाई composite कुञ्जी चाहिन्छ। एक–स्तम्भे कुञ्जीमा 1NF ले नै 2NF दिन्छ।
  • Each form includes the ones before it, so always work 1NF → 2NF → 3NF and show the intermediate tables. हरेक रूपले अघिल्लोलाई समेट्छ, त्यसैले सधैं 1NF → 2NF → 3NF क्रममा काम गर्नुहोस् र बीचका तालिका देखाउनुहोस्।
  • After splitting a table, keep the foreign key that points back — otherwise the link between them is lost. तालिका छुट्याएपछि फर्केर देखाउने foreign key राख्नुहोस्, नत्र जोडाइ हराउँछ।
